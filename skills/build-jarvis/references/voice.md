# Voice engineering and acoustic proof

## Capture and device routing

Enumerate actual input/output devices and verify the chosen device IDs survive the intended restart/reconnect behavior. Account for sample rate, mono/stereo, signed sample format, endian order, gain, resampling and frame timing. Device names, OS defaults and an app's saved selection can disagree. Confirm the process has an active capture stream, not only a permission flag.

Microphone permission, speech recognition, system audio capture, screen recording and Accessibility are distinct. Browser grants can belong to an origin, profile or debugger connection; preserve the necessary connection through the test. A page retaining a microphone icon after a permission helper disconnects is insufficient. Inspect actual native stream/activity before injecting an utterance.

For a virtual audio lab, use separate microphone-injection and speaker-capture buses. Record three independent controls: intended input reaches the microphone; known speech played to the output bus reaches the speaker recording; speaker output does not leak back into input. Keep test route names task-owned, save defaults and restore them after. Use real household/hardware audio when virtual routing cannot exercise the native capture path.

Start recorders, wait until they are genuinely receiving frames, then inject the complete phrase. Fixed sleeps alone can lose the start of an utterance. Capture silence before/after as needed, record source gain and inspect peak/RMS/clipping. Nonzero audio can be notification tones, clicks or noise; independently transcribe intelligible speech. Close/flush the recording before ASR: an open WAV can have an unfinished header and yield a false empty transcript.

Keep original recordings. Make clearly named analysis copies for resampling, mono conversion or service size limits. Record the conversion, duration and channel. An ASR timeout or oversized upload makes that observation incomplete, not a candidate speech failure. Sensitive household/account audio belongs in private evidence with only sanitized observations published.

## Wake and turn-taking

Choose activation deliberately: wake word, a bounded continuous session, push-to-talk or a native device gesture. Indicate the listening state and provide an immediate physical/software mute. Continuous capture does not require continuous retention. Measure false accepts/rejects in the user's noise, speaker distance, language and playback conditions; transcripts containing a short wake fragment are a poor activation boundary.

Capture a bounded in-memory pre-roll so detection latency does not discard the beginning of the utterance. Measure the actual processed input as well as the raw virtual microphone: track existence alone does not prove that usable frames reach the detector during playback. For isolated-graph diagnosis, compare explicit browser processing settings one condition at a time and retain the physical echo-cancellation limitation. Any diagnostic audio retention must be opt-in, scoped and cleaned up.

VAD answers whether speech-like audio is present; turn detection decides whether a person has finished. Tune endpointing, silence thresholds and minimum utterance length against natural pauses. Capture timestamps and false interruptions. Explicitly handle accidental wakes, overlapping speakers, long pauses, self-playback and recognition uncertainty.

Use echo cancellation where the native stack supports it, with the correct playback reference and timing. Distinguish echo cancellation from a completely isolated virtual graph. A synthetic no-feedback result does not establish acoustic echo performance in a room. Test loudspeaker, headphones and Bluetooth routes separately.

## Streaming and playback

Track audio from generated bytes to decoded samples, queued playback, actual sink output and completion. Streaming token/text responses may still use fully buffered synthesis. A synthesis-success callback is not proof a decoder played anything. Release capacity and emit terminal playback state on success, abort, network failure and client disappearance.

Validate container/MIME/sample-format compatibility with the actual native player. Raw PCM at HTTP 200 can fail a browser media element expecting a container. Preserve the error and diagnose that boundary; use a supported output format or explicit adapter rather than marking the whole speech provider unavailable.

Browser automation often launches with audio muted. Inspect actual launch arguments and context settings. Virtual displays, native permissions and headless mode can change app behavior. Test an independent speaker-route control before grading an empty output recording. On macOS, voice-processing capture can behave differently from simple CoreAudio capture and may reject or silence loopback inputs; localize that limitation and use supported physical/native tests.

## Barge-in has two targets

Define conversational interruption separately from task cancellation. On real user speech, stop queued/current playback, cancel or supersede the relevant conversation generation, and process the new turn. Worker cancellation follows the user's separate task intent and ownership policy. Old text/audio callbacks must not resume interrupted output or claim completion later.

Scope playback callbacks and rejected playback promises to both the current generation and player instance, including error handlers. Clearing an interrupted player's source can trigger a late media error; that expected abort must not overwrite a newer successful turn with a false failure banner. Preserve genuine errors from the current player. Inspect the resulting UI as well as the captured sound after interruption.

To test conversational interruption:

1. Request a long spoken response and verify actual spoken output has begun.
2. Confirm the microphone remains active during playback.
3. Inject a distinct new question while the real response is audible.
4. Capture/transcribe input and output independently; verify old speech stopped and the new answer was spoken.
5. Inspect the event timeline and UI interruption state, then a subsequent fresh turn.

A fixed-time interrupt can arrive before output starts. Energy gating can trigger on an interface beep. Require intelligible pre-interruption speech and a real new answer before calling it a barge-in pass. A successful “Four” in the text UI with a waiting speech approval card is a partial exchange.

## Measure the intended experience

Report end-of-speech to first actually played response audio, plus capture/endpointing/recognition/model/synthesis/playback breakdown. Compare identical workloads and temperature/warm-cache conditions. Total phone-call duration includes ringing and user response and is not equivalent to voice latency.

Test long sessions, silence, disconnection, device removal, route changes and sleep/wake. Bound reconnection attempts, preserve mute intent and make renewed microphone activity visible. Decide whether control loss stops the conversation, pauses it or requests reconnection; verify the chosen policy rather than automatically restarting a microphone indefinitely.

## Phone and wearable conditions

Qualify foreground, immediate background, background after several minutes, locked screen, notification restrictions, DND/Focus, built-in audio, earbuds, car audio and reconnect separately. A foreground success does not qualify unattended use. Record actual app/OS versions and the configured service timeout; obtain fresh readiness before placing a disruptive call.

An answered call can still have no uplink transcript. A service's `missed_call` label does not override the user's observation that it rang and was answered. Compare phone delivery, prompt playback, microphone capture, uplink, recognition, end-of-turn and returned result. OS microphone-service restrictions or Bluetooth routing are hypotheses until device/service evidence establishes them. Preserve successful earlier background calls as well as later failures.

Simulator builds qualify compilation and selected UI paths. Physical microphone, background delivery, Bluetooth, cellular handoff, glasses SDK registration and signed-device capabilities need their corresponding real hardware/credentials. A phone or tablet offered by the user unlocks only the paths it actually supports.
